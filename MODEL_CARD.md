###### Description

`google/tapas-large-finetuned-wtq` is the large TAPAS checkpoint released by Google Research (Herzig et al., arXiv:2004.02349; intermediate pre-training by Eisenschlos et al., arXiv:2010.00571), redistributed on the Hub with a card written by the Hugging Face team, and pinned here to revision `f58317ab2577d17647d9acafa790c744a0388b30` — the upstream default `reset` branch (`tapas_wtq_wikisql_sqa_inter_masklm_large_reset`), which resets the position index at every cell. It is a BERT-style bidirectional encoder — 24 layers, hidden size 1024, 16 attention heads, 30 522-entry WordPiece vocabulary, seven extra token-type embeddings for segment, column, row, numeric rank and relation ids (snapshot `config.json`) — pre-trained with masked language modelling and an intermediate table-entailment task on Wikipedia tables, then fine-tuned in a chain on SQA, WikiSQL and finally WikiTableQuestions with two heads: cell selection and aggregation (`aggregation_labels`: NONE, SUM, AVERAGE, COUNT). At inference this package flattens one table and one question into `[CLS] question [SEP] table`, runs the encoder once, selects every cell whose mean token sigmoid probability exceeds `CELL_THRESHOLD = 0.5` and takes the argmax aggregation — the exact semantics of the upstream `TapasTokenizer.convert_logits_to_predictions`, which the loader calls. The model emits no number; the `numeric_answer` field is computed by this package from the selected cell strings and labelled by `numeric_answer_source`. Nothing is fine-tuned, adapted or conditioned in this repository. What it adds is packaging: the `TAPASTableQAPipeline` class in `src/tapas_table_qa_pipeline/pipeline.py`, digest verification of the local snapshot (`verify_snapshot`, `stage_missing_files`), table and question validation against named ceilings, a fixed output contract, the `denotation_accuracy` metric helper, and the `validate_inputs`/`evaluation_report` stage helpers.

#### Intended Use and Limitations

###### Primary Intended Uses

One task: answering a natural-language question about a single small table. Input a table as `{column: [cells]}` or `[{column: cell}, ...]` with every header and cell a string (1–`MAX_ROWS = 64` rows, 1–`MAX_COLUMNS = 32` columns) and one question string; output the selected `cells` with their `coordinates`, the `aggregation` operator, the upstream-style `answer` string (`SUM > 1,846,513, 1,776,949`), and the pipeline-computed `numeric_answer`. Envisioned domains are the ones the WikiTableQuestions benchmark represents — factual lookups, counts, sums and averages over short, self-contained tables of the kind found in encyclopaedia articles, reports, catalogues and dashboards, where a human will read the selected cells alongside the number. In a larger system the pipeline is a baseline table-reader and an explanation-producing component (it always shows which cells it used), not a decision engine; the upstream card states only "You can use this model for answering questions related to a table".

###### Primary Intended Users

Machine-learning engineers, NLP researchers and application developers evaluating a table-QA baseline in research prototypes, internal enterprise tooling or the DIMER model workbench. The pipeline assumes its users understand that TAPAS reads a table as lower-cased text (numbers must arrive as strings and are parsed back only for the pipeline's own arithmetic), that cell selection is a fixed 0.5 sigmoid threshold and operator choice an argmax — neither a calibrated probability — that the model always returns some cells and some operator even for questions the table cannot answer, that a table longer than 512 WordPiece tokens is truncated rather than rejected and the result must be read for `truncated`/`rows_kept`, and that the WTQ dev accuracy the upstream card reports (0.5097) means roughly half of benchmark questions are answered wrongly. It is not designed for hobbyist "point and trust" use.

###### Out-of-scope use cases

1. **Capability boundary:** not conversational, multi-turn table QA (the SQA setting; each call is independent); not free-form computation — only NONE/SUM/AVERAGE/COUNT exist, so a difference, ratio, maximum or date arithmetic cannot be expressed and the model will return the nearest operator it has; not text-to-SQL, not multi-table joins, not extractive QA over prose (use the sibling `roberta-squad2-question-answering-pipeline`); not fine-tuning; not batch questions in one forward pass.
2. **Input boundary:** headers and cells must be `str` (`TypeError` otherwise — stringify numbers yourself); tables outside 1–64 rows or 1–32 columns are rejected with `ValueError`; a cell over `MAX_CELL_CHARS = 200` or a question over `MAX_QUERY_CHARS = 500` characters is rejected; a flattened table over `MAX_TOKENS = 512` WordPiece tokens is **truncated** by the tokenizer (cell text trimmed to a common token count, then trailing rows dropped) and reported, never rejected; non-English tables, nested or merged cells, and numbers written with non-ASCII separators or units degrade without any warning beyond `unparsed_cells`.
3. **Decision boundary:** not for autonomous or high-impact decisions — financial reconciliation, compliance reporting, eligibility determinations, clinical or safety figures — without a human reading the selected cells against the source table and a locally measured denotation accuracy; not for inferring attributes of individuals from tables about people.

#### Factors

###### Groups

The pipeline is not human-centric by design: its inputs are tables and questions, and its outputs are cell references and arithmetic. It becomes human-centric whenever the table describes people (staff rosters, patient lists, demographic statistics), and then the WikiTableQuestions and Wikipedia pre-training data shape which column names, entity names and phrasings the model reads reliably — English, Wikipedia-style tables about the topics Wikipedia covers. Neither the upstream card nor the papers report any group-level evaluation of the pre-training tables or of WTQ, and this repository ran no fairness evaluation; the upstream card's "Intended uses & limitations" section says nothing about bias. The obligation therefore transfers to the operator: before any deployment whose tables describe people, run a paired-question probe (the same question over rows differing only in a group attribute, compared on selected cells and operator) and a denotation-accuracy evaluation stratified by the groups relevant to the application, and treat a material gap as a blocker.

###### Instrumentation

No physical sensor produced the training data: it is text and HTML tables. Upstream discloses pre-training on "a large corpus of English data from Wikipedia" — raw tables and associated texts, with MLM and intermediate-pre-training examples generated automatically ("millions of syntactically created training examples … synthetic as well as counterfactual statements") — and fine-tuning on SQA, WikiSQL and WTQ, the last "converted into the format of SQA using automatic conversion scripts" (pinned README "Model description" and "Training procedure"). The instrument characteristics that reach the model are therefore Wikipedia's table markup, the crowd-sourced question writing of those benchmarks, the automatic conversion scripts, and the tokenizer: lower-casing WordPiece with a 30 522-entry vocabulary, per-token row/column ids, and numeric-rank ids derived by the tokenizer's own number parser. At inference the only instrument is the snapshot tokenizer (`vocab.txt`, `tokenizer_config.json`); OCR noise, unusual Unicode, units embedded in cells and non-ASCII digit separators fragment into sub-word pieces or fail numeric annotation, and the pipeline reports token counts and `unparsed_cells` but does not detect encoding drift or a changed table-extraction procedure.

###### Environment

Operating environment: Python 3.12 with `torch==2.14.0`, `transformers==4.57.6`, `tokenizers==0.22.2`, `pandas==3.0.5`, `numpy==2.5.3` (exact pins in `pyproject.toml`), float32. `from_pretrained(device=None)` picks `cuda:0` when available, else CPU; this repository's smoke ran on CPU only (Windows venv, `CUDA_VISIBLE_DEVICES=-1`, `device="cpu"`): loading and digest-verifying the 1.35 GB snapshot took 6.83 s, and three `answer` calls on a 4×3 table took 0.95 s, 0.50 s and 0.51 s; a separate 64-row probe took 0.70 s. This is a roughly 337 M-parameter encoder (1 346 985 282 bytes of float32 weights ÷ 4; 24 layers, hidden 1024), so per-question latency is measurable on CPU and the `model.safetensors` download is 1.35 GB. The CUDA path is untested in this repository. Runtime compatibility: the `TapasTokenizer` in `transformers==4.57.6` predates `pandas==3.0.5`, so the loader builds the table with `dtype=object` through a `DataFrame` subclass whose `iterrows()` yields position-indexed rows; without it the pinned tokenizer raises on every call. Data environment: inputs are assumed to be small, flat, English tables resembling Wikipedia's, with one header row, one value per cell and numbers written as plain decimals with optional thousands commas; behaviour on wide or long tables (truncation loses rows and cell text), on domain jargon, on non-English text, or on numbers with units, currencies or ranges is not measured here and is expected to degrade — a 64-row probe in this repository answered a single-cell lookup with the operator `SUM`.

#### Metrics

###### Performance Measures

The pipeline reports one performance measure, `denotation_accuracy(results, golds)`: the fraction of questions whose predicted denotation equals the caller-supplied gold — a numeric gold compared with `numeric_answer` (or with the single selected cell parsed as a number under NONE) to an absolute tolerance of 1e-6, otherwise the selected cell strings compared with the gold strings as multisets after lower-casing and whitespace collapse. It is the WikiTableQuestions criterion, chosen because the task's output is a denotation (a set of cells or the number an operator yields), not a probability, a ranking or a span: discrete correctness is the only thing a table question has a ground truth for, and cell-level precision or aggregation-operator accuracy would each miss half of what makes an answer right. The public `evaluation_report()` helper reports it as `sample-sanity` when golds are supplied and `not-measurable` otherwise, with `needs` naming the gold denotations that would make the task measurable. The smoke run scored 1.0 on three author-written questions — a plumbing check, not an accuracy. Upstream reports a WTQ dev accuracy of 0.5097 for this `reset` checkpoint (pinned README "Results"); that is upstream-reported, not measured here, and the pipeline has not reproduced it.

###### Decision thresholds

Two decision rules are applied on every call and both are inherited from the upstream `convert_logits_to_predictions`: a cell is selected when the mean sigmoid probability over its tokens exceeds `CELL_THRESHOLD = 0.5` (the upstream `cell_classification_threshold` default; a value the pipeline passes explicitly and does not expose as a parameter), and the aggregation operator is the argmax over the four aggregation logits — an implicit threshold with no minimum margin, so a near-tie between SUM and NONE still yields one of them. No acceptance threshold was set during development, and none is shipped on the aggregation logits (they are returned raw in `aggregation_logits`) because the fine-tuned head is not calibrated and the cost of a wrong number depends entirely on the deployment. A deployment that needs one must choose it on its own labelled questions, trading a wrongly confident number (false positive: a SUM over the wrong cells, an operator applied to a single cell) against an unanswered question (false negative) for its application; the `numeric_answer` field is `None` only when a selected cell does not parse, never because the model was unsure.

###### Approaches to uncertainty and variability

`denotation_accuracy` is estimated by a single pass over whatever labelled questions the caller supplies; the smoke's 1.0 is over three questions on one table with no dispersion, and `evaluation_report` records `estimation: "single sample, no dispersion estimate"` for exactly that reason. Inference is deterministic given the same weights, device and library versions: dropout is disabled by `model.eval()`, there is no sampling, and no seed is required; small numeric differences between CPU and GPU kernels can flip a cell whose mean probability sits near 0.5 or an operator whose logits are near-tied. The per-cell probabilities and the aggregation logits are not calibrated — the upstream head was trained with a weak-supervision objective (`use_answer_as_supervision`, `answer_loss_cutoff` in the config) whose scores are not probabilities of correctness — so a caller who needs a confidence must fit a calibration map on their own labelled questions; the pipeline exposes the raw `aggregation_logits` to make that possible and nothing else.

#### Ethical considerations and biases

###### Data

Upstream discloses pre-training on English Wikipedia tables and associated text, intermediate pre-training on automatically generated entailment statements, and fine-tuning on SQA, WikiSQL and WikiTableQuestions — all three built from Wikipedia tables with crowd-sourced questions (pinned README "Model description", "Training procedure"; Pasupat & Liang 2015 for WTQ); the disclosure stops there — no per-table licensing, no consent, no demographic composition. Wikipedia tables include biographies, election results, sports rosters and other records about named living people, so personal data in the training data is not ruled out, and a masked-language-model encoder can carry memorised associations into cell selection. This repository distributes code, tests and documentation; the 1.35 GB snapshot (`model.safetensors`, `config.json`, tokenizer files, upstream `README.md`) is git-ignored and staged locally under `weights/tapas-large-wtq/` with a manifest, and no sample data or datasets are shipped beyond the synthetic 4×3 table authored in the tests and notebook. The operator must audit the tables they submit for personal, confidential or proprietary content and must not log or retain selected cells from such tables without the same controls they would apply to the table itself; the pipeline performs no such check.

###### Human Life

The pipeline is not intended for decisions in health, safety, criminal justice, employment, credit, housing or any other domain central to human life, and it has not been validated or certified for any of them by anyone. Its only validation is the offline unit suite (23 tests) and the CPU smoke run recorded in this repository. Where a sensitive use is foreseeable — for example summing a medication table, reading a benefits eligibility table, or counting incidents in a safety log — it is admissible only with a human reviewer checking the selected cells against the source table on every consequential outcome, an independent domain evaluation of denotation accuracy on representative tables, and whatever regulatory clearance the domain requires.

###### Mitigations

Implemented and inspectable in `src/tapas_table_qa_pipeline/pipeline.py`: (1) supply chain — `MODEL_REVISION` is a 40-hex commit; `stage_missing_files` refuses a manifest naming another model or revision and fetches only manifest-listed files at the pinned revision, and `verify_snapshot` re-hashes every file in `weights/tapas-large-wtq/dimer-base-manifest.json` and raises on the first size or SHA-256 mismatch before any weight is loaded; the Hub path is taken only with `allow_download=True` and always with `revision=MODEL_REVISION`; `trust_remote_code=False` on both tokenizer and model; model libraries are imported only after the snapshot check passes (`tests/test_import_boundary.py`). (2) Input integrity — `_check_table` normalises both table shapes and rejects non-`str` headers or cells, unequal column lengths, rows whose keys differ from the header, and tables outside 1–`MAX_ROWS`/1–`MAX_COLUMNS`; `_check_query` rejects non-`str`, empty and over-`MAX_QUERY_CHARS` questions; `answer` raises `RuntimeError` if the backend returns a coordinate outside the table, and reports `truncated`, `rows_kept` and `tokens_before_truncation` so tokenizer truncation is never silent. The public `validate_inputs()` helper applies those same checks through the same private functions and returns one input manifest (schema, ceilings, table shape, numeric-cell count, per-question entries, verdict, findings). (3) Reproducibility — exact `==` dependency pins, `model.eval()`, float32, and `model_id`/`model_revision`/`device`/`source`/`decision_rule` in every result. (4) Refusals — no fine-tuning, no batch questions, no conversational state and no raw token logits are exposed; a missing snapshot with `allow_download=False` raises `FileNotFoundError`. (5) Labelling — every number the pipeline computes carries `numeric_answer_source` and the cells it came from, so a reader can never mistake the arithmetic for a model output. No statistical mitigation (debiasing, re-weighting) is applied: the weights are redistributed unmodified.

###### Risks and harms

Confidently wrong numbers: the model always selects some cells and some operator, and the pipeline's arithmetic turns them into an exact-looking figure — a SUM over the wrong rows, an AVERAGE over a partial column, an operator applied to a single cell (observed on the 64-row probe) — and the operator bears the harm when the figure is reported without the cells being checked; likelihood is high on questions outside the benchmark's phrasing, given the upstream dev accuracy of about 51 %. Silent context loss: a table over 512 tokens is truncated, so a sum or count runs over the rows the model saw, not the rows the caller supplied; the result says so, but only if read. Number-parsing gaps: a cell like `1.2M`, `$3,000` or `12–15` does not parse, `numeric_answer` becomes `None`, and a downstream system that expected a number fails or defaults. Bias reproduction: cell selection and operator choice reflect the Wikipedia-derived training tables, so questions about people or places under-represented there are answered less reliably, and data subjects bear the harm when such answers feed a decision. Memorised associations from Wikipedia can surface as spuriously selected cells. Automation bias: a reader shown highlighted cells and a number checks them less carefully than the raw table. Magnitude ranges from a wrong figure in a report to a wrong eligibility or reconciliation decision.

###### Use cases

The pipeline must not be used for surveillance, biometric or demographic profiling, or social scoring — including aggregating tables of individuals to infer protected attributes, or counting and summing records about people to rank or target them. It must not support unlawful discrimination in employment, housing, credit, insurance, education or healthcare access, for example by answering eligibility or screening questions over applicant tables without human review. It must not power deceptive or manipulative applications such as presenting its computed figures as audited or authoritative statistics, or fabricating table-backed claims about real people or organisations. Any use that violates the Apache-2.0 terms of the upstream weights or the DIMER deployment terms is prohibited. The developers identify no further prohibited use beyond these because the model's outputs are cell references, one of four operators, and arithmetic the pipeline performs in the open.

## Input/output contract

- `TAPASTableQAPipeline.from_pretrained(device=None, weights_dir=None, allow_download=False)`
- `answer(table, query)` — `table`: `{column: [cells]}` or `[{column: cell}, ...]`, every header and cell `str`, 1–64 rows, 1–32 columns, cells ≤ 200 chars; `query`: `str`, 1–500 chars. Returns `{"cells": [str], "coordinates": [[row, col]], "aggregation": "NONE"|"SUM"|"AVERAGE"|"COUNT", "answer": str, "numeric_answer": float|None, "numeric_answer_source", "unparsed_cells": [str], "aggregation_logits": {label: float}, "n_tokens", "tokens_before_truncation", "rows_kept", "truncated", "decision_rule", "device", "source", "model_id", "model_revision"}`; `coordinates` index data rows (0 = first row below the header); `answer` is the upstream pipeline's string form (`cells` joined with `, `, prefixed `<AGG> > ` when an operator was chosen).
- `denotation_match(result, gold)` / `denotation_accuracy(results, golds)` — WTQ denotation criterion; `gold` is a number, a string or a list of cell strings.
- `parse_number(cell)` / `compute_numeric_answer(cells, aggregation)` — the arithmetic behind `numeric_answer`, exposed so its rules are inspectable.
- `validate_inputs(table, queries, *, names=None)` → input manifest; `evaluation_report(results, golds=None, *, sample_kind="synthetic")` → evaluation report.
- `verify_snapshot(path=None)` — returns the manifest dict with `path`; raises `FileNotFoundError` / `ValueError`.
- `stage_missing_files(path=None, *, allow_download=False, downloader=None)` — returns the relative paths fetched (`[]` if none were missing).
