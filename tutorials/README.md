## Conformance notes

_Requirement identifiers in these notes (for example `ST1`, `PAR3`, `DAT24`, `EVAL21`) are the NOTEBOOK_SPEC 1.1 numbering they were written against; NOTEBOOK_SPEC 2.0 renumbered its sections and the pull request that migrated this repository reports conformance against the 2.0 pre-flight checklist (§26) and report format (§30)._

- **Standalone carrier (ST1–ST6):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/tapas_table_qa_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 6-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins (including `pandas==3.0.5`, which the carried module needs only inside `from_pretrained`). `metadata.dimer.generated_from` records the repository, the revision generated from, the module's SHA-256, and the generator version.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Role stages:** `validate_inputs` (DAT24) writes `outputs/tapas_table_qa_input_manifest.json` — the schema and ceilings, the table shape and how many cells parse as numbers, one entry per question, the verdict, and one recorded rejection finding (a table with a non-string cell, rejected by the same `_check_table` the `answer` method uses); `evaluation_report` (EVAL21) writes `outputs/tapas_table_qa_evaluation_report.json`, whose metric id `denotation_accuracy` is the repository's own helper (EVAL2). On the synthetic sample the author's three expected answers are passed as golds, so the verdict is `sample-sanity` with a single-sample estimate and no dispersion; without golds (BYOD) it is `not-measurable` and `needs` names the gold denotations that would make the task measurable (EVAL9).
- The notebook exercises `TAPASTableQAPipeline` carried verbatim in the notebook rather than reimplementing model loading; the pipeline pins the immutable upstream revision, stages the missing snapshot file through the package's `stage_missing_files(..., allow_download=True)`, loads only from a digest-verified local snapshot (`verify_snapshot`), and refuses remote model code. No cell outside the carried module calls `transformers`, `huggingface_hub` or `pandas` (the BYOD CSV is read with the standard library).
- Score semantics (UNC1–UNC4): the cell decision is a fixed sigmoid threshold (`CELL_THRESHOLD = 0.5`, the upstream default) and the operator decision is an argmax over four logits; neither is a calibrated probability, the pipeline ships no acceptance threshold on the aggregation logits, and the caller owns any cut-off. The `numeric_answer` is the pipeline's arithmetic over the selected cell strings, labelled by `numeric_answer_source`, never a model output.
- Ceilings `MAX_ROWS`, `MAX_COLUMNS` (reject), `MAX_TOKENS` (the tokenizer truncates — cell text trimmed to a common token count, then trailing rows dropped — and `answer` reports `truncated`, `rows_kept`, `tokens_before_truncation`), `MAX_QUERY_CHARS`, `MAX_CELL_CHARS`, `AGGREGATIONS` and `CELL_THRESHOLD` are surfaced before the model runs (DAT22/DAT23); the notebook never alters the table.
- The model card's smoke observations (`Cebu`; `COUNT` → 4.0; `SUM` → 3,623,462.0; a `SUM` over a single cell on a 64-row probe) are quoted as single measurements, not expected values, and the upstream WTQ dev accuracy (0.5097) as upstream-reported, not measured. Recorded `SHOULD` deviation: EVAL11 (no baseline — a majority or random-cell baseline is not meaningful on three questions).
- The default sample is synthetic and authored in code; `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
